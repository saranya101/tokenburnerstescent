# Durable synthetic bank release gate

The mock bank has two production modes. `PARLANCE_BANK_DATABASE_SNAPSHOT=true` reads the isolated PostgreSQL customer and rejects every bank write. Durable mode is disabled by default. It requires `PARLANCE_BANK_DURABLE_EXECUTION=true` and `PARLANCE_ISOLATED_SYNTHETIC_EXECUTION_APPROVED=true`, plus the exact approved Railway project, environment, application service, and private PostgreSQL target. Production refuses to start in the in-memory mode.

The `20261016000000_synthetic_bank_operation_ledger` migration adds a persistent operation ledger, a persistent asset-quote table, and amount binding to FX quotes. Do not apply it to Railway without confirming the approved isolated synthetic database and obtaining approval for that specific migration. The current public safe mode, passkey enrollment gate, and execution gate remain separate. The new `PARLANCE_PUBLIC_PASSKEY_EXECUTION_ENABLED` flag defaults to false and must stay false until a real HTTPS browser passkey ceremony and customer-bound API execution have been verified.

Read-only inspection on 2026-10-16 confirmed the production Postgres service has 13 completed migrations, one synthetic customer, two accounts, 15 saved payees, one holding, and the approved Auth0 subject mapping. The ledger migration is absent. PostgreSQL also reports that the database was created with collation version 2.41 while its current OS provides 2.36. Durable mode now rejects reads and writes when PostgreSQL 15+ reports a database-default collation mismatch. Before enabling it, obtain approval for a maintenance window, rebuild affected indexes, refresh the database collation version, and verify the warning is gone. Never merely refresh the version to suppress the warning without rebuilding indexes.

Within a single synthetic bank operation, PostgreSQL serializable transactions and a customer row lock atomically update balances, holdings, state versions, and the unique idempotency record. A stale snapshot fails before mutation. A repeated key with the same request returns its persisted result; a changed request fails. If the HTTP response is lost after commit, the API can reconcile by looking up the key. A reviewed multi-step plan is not one database transaction: earlier steps may settle while a later step fails. The API must retain its `PAUSED` or `UNKNOWN` state and reconcile every step. No external real-bank exactly-once guarantee is claimed.

The integration test `services/mock-bank/src/durable-bank.integration.test.ts` requires a disposable local PostgreSQL database named `parlance_test_*`, with pgvector and all migrations installed. It covers restart recovery, concurrent state-version conflicts, transfer → FX → AAPL purchase, rejected writes, and response loss after commit. It never falls back to the production database. `PARLANCE_DURABLE_DB_TEST_URL` must point to that local test database.

Release sequence: verify the Railway target and migration history; obtain approval for the collation repair and new migration; rebuild affected indexes and refresh the collation version; apply only the new migration; run authorized isolated financial-write tests; verify a real browser passkey enrollment and approval against the Railway origin; review execution receipts and cross-customer denials; then set the three execution flags and redeploy the existing service. Keep Android financial execution disabled until native passkeys and Digital Asset Links are separately verified.

# C3A deterministic planner

`compile_goal` accepts a grounded `GoalContractV1`, a `BankStateSnapshotV1`, optional persistent hard rules, a `PolicyEngine`, and an internal depth limit (default four). `compile_with_diagnostics` additionally returns search metrics. The HTTP endpoint still calls the same compiler with its existing request shape; persistent rules are supplied by a trusted caller to the Python API until the surrounding service passes them through. The compiler does not resolve names or execute bank actions.

The candidate enumerator derives concrete transfers, targeted same-currency moves, and quote-bound FX conversions from the current simulated state. It sorts candidates with the C1 operation key. FX source amounts are found by exact Decimal half-even output checks. Bounded BFS calls the C2 policy engine, C1 immutable simulator, and C2 constraint evaluator for every transition. It prunes excluded funding, known maximum-cost breaches, and other monotonic failures immediately. Minimum-balance constraints are final gates where a later credit could restore liquidity. A canonical state digest plus route metadata tracks visited paths, while each path's digest history prevents cycles.

A money-delivery goal is complete only after a simulated `TRANSFER` of the exact amount and currency to the grounded beneficiary ID. A `MOVE_FUNDS` goal is complete only after an exact move to its grounded destination (and source, if specified). This completion fact is internal because V1 has no beneficiary balance. C3A never synthesizes `PAY_BILL`, `BUY_ASSET`, or `SELL_ASSET` steps.

All valid routes within the depth bound are ranked by the goal's ordered preferences: known comparable total cost, FX count, step count, or first funding source. C3B hardening returns `AMBIGUOUS_VALID_PLANS` when the best preference score still leaves materially different routes, including when there are no preferences. Materially equivalent routes use a stable operation key as a tie-break. If total costs cannot be compared in one trusted currency, `MINIMIZE_TOTAL_COST` returns `COST_COMPARISON_UNAVAILABLE`. No new public result variant was added.

Plan IDs derive from canonical goal, snapshot, hard rules, policy allowlist, compiler version, and chosen route. Sequential step IDs derive from the plan ID. `planHash` hashes canonical plan fields excluding itself. FX validity binds exact quote IDs and the earliest expiry. Projected balances come from the final simulated state. `FinancialPlanV1` has no `totalEstimatedCost` field, so C3A does not add one. The internal `SearchDiagnostics` records explored states, evaluated candidates, maximum reached depth, and solver calls. Solver calls are zero for concrete C3A transitions because C1 and C2 already decide their exact integer feasibility; the C2 Z3 helpers remain available for later symbolic bounds.

`POLICY_BLOCKED` represents bank permission failures such as a blocked beneficiary, unavailable required service, or disallowed action. `UNSAT` covers financial infeasibility, customer constraints, unsupported goals, route bounds, and unresolved material choice. This is initial planning only: it does not revalidate or replan after execution changes.
